# 計測運用と定期実行

## 手動実行を先に通す

最初に一記事だけで次を確認する。

1. ブラウザ版ダッシュボードで対象期間、記事またはアカウントのscope、集計時刻を確認できる。
2. 現行5指標を別項目として読み、流入元をアカウントscopeにだけ置ける。
3. 未収集と取得不能をstatusと理由で残せる。
4. local recordとvalidatorがpassする。
5. 旧`views`と現行指標を混ぜず、結果が記事評価や次テーマの自動決定になっていない。

## scheduled taskを提案する条件

手動実行後、利用者が継続計測を希望する時だけ、adapterは次を表示して承認を取る。

- 対象workspaceの絶対path。
- アカウント観測の有無と、対象にする公開記事の範囲。
- 比較に使う完了期間。標準案は当日を含まない同じ長さの二期間とし、目的が違えば減らせる。
- 希望する曜日と時刻。土曜日は標準案であり固定値ではない。
- local fileと必要な画面へアクセスする実行環境。
- 書き込み先が`metrics/history.jsonl`だけであること。
- task作成、変更、停止がlocal Skillとは別の外部状態であること。
- 対象がready確認済みの`📊 note｜計測・公開ログ`であり、strategy heartbeatより先に実行すること。

利用者が承認した時だけhostの公式scheduled task機能を使う。raw schedule表現や特定製品の一時的なUI文言をcoreへ固定しない。

## 実行promptの意味

実行promptは、対象workspaceの`STUDIO.md`、継続指示、`note-tracker`を読み、戦略に保存された目的から必要な観測範囲を選び、対象期間、scope、集計時刻、現行5指標、必要な場合だけアカウント流入元をstatus付きで記録し、validatorを実行する内容にする。全記事や売上を毎回必須にせず、意図して省く値は`not_collected`とする。公開、編集、下書き操作、テーマ決定を含めない。完了時は取得時刻、status、失敗理由をworkspaceへ残し、後続の戦略担当が古い値や途中期間を最新の完了比較と誤認しないようにする。

## 失敗時

- PCやアプリが動作していない: 実行済みとせず、次回または手動実行へ回す。
- ログインや画面変更で取得できない: 正確な値を作らず`fetch_failed`または`not_visible`にする。
- local fileへ書けない: 会話へ観測結果を返し、保存済みと報告しない。
- lockが残る: 別processを確認するまで削除しない。
- 週間企画は計測失敗だけで止めない。取得できた材料と本人の方針で続ける。
