# 戦略契約

## 目的

利用者の目的、書きたい気持ち、本人固有の材料、読者価値、継続可能性を一緒に見て、次に取る行動を提案する。表示、スキ、コメント、検索、相談、売上を一つの成果へまとめず、流行やAIの推奨だけで方針を決めない。

## 読む順序

1. `workspace.json`と`strategy/operating-settings.json`で対象workspaceと運用状態を確認する。
2. `strategy/strategy.md`と`profile/creator-profile.md`で目的、読者、テーマ、継続条件を読む。
3. 直近の週間計画があれば最新revisionだけを現在状態として読み、`recommended`と`confirmed`を区別する。
4. `source-cards/cards.jsonl`から最新有効revisionだけを選ぶ。生ログ全体は読まない。
5. 記事台帳と指標履歴が利用可能な時だけ読む。空または取得不能は`0`ではない。

## 候補の判断

固定点数や秘密の重み付けを使わず、候補ごとに次を説明する。

- 本人が今書く意味。
- 中心となる具体的な場面、判断、変化。
- 読者が読む理由。
- 過去記事との差。
- 現在性または今週書く理由。
- 必要な調査と、まだ足りない本人情報。
- 今週使える時間との釣り合い。

材料が薄い時は候補数を減らし、`needs_more_source`として記録する。予定本数は上限の目安であり、未確認の経験や引用を作って埋めない。

## 指標と公開情報

指標は[目的別の参考指標分析](goal-aware-analysis.md)に従い、その回の依頼と既存プロフィールから主レンズを一つ、必要な時だけ副レンズを一つ選ぶ。項目、scope、対象期間、画面の集計時刻、取得状態を分ける。旧`views`を新しい`impressions`や`page_views`へ変換せず、一回の増減から因果を断定せず、次の記事で小さく確かめられる問いへ変える。本人が残してよかった記録は、反応が小さくても候補にできる。

公開情報は、制度、季節、製品仕様、現在の話題等が候補の価値を変える時に使う。公開情報、本人の経験、推測を同じ事実として混ぜない。

## 承認境界

候補提示と`strategy_recommendation`は提案であり、利用者の週間計画確定ではない。定期実行は未確定の推奨として保存できる。利用者が採用、修正、保留、差し替え、休止、別テーマを決めた場合は`user_selection`として保存する。計画選択は記事本文、画像、note下書き、公開、scheduled task作成の承認ではない。
